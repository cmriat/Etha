# 训推权重同步还在 all-gather 整张大 weight？开源项目 Etha 用零冗余把显存天花板拆了

> 备选标题
> - 训推权重同步告别"搬整张大模型"：开源项目 Etha 用零冗余把显存天花板拆了
> - 21GB 的 MoE 权重怎么跨集群同步？Etha：只搬该搬的那一份，零拷贝零冗余
> - PyTorch 原生的 M-to-N 张量重分布，Etha 专治 RL 训推参数同步

![Etha：M-to-N DTensor 重分布架构概览](etha_arch.png)

在训推分离（disaggregated RL）逐渐成为大模型后训练主流的今天，一个看似不起眼的环节正悄悄变成显存杀手——训练好的权重，怎么高效同步给推理引擎？

随着 MoE 模型越做越大，单个融合权重（如 `gate_up_proj`）动辄 8GB、14GB、21GB。传统"先把完整权重拼出来、再广播下去"的方案，让每张卡都要额外吃下两三份完整大权重，稍不留神就 OOM。

最近开源的 **Etha**（[github.com/cmriat/Etha](https://github.com/cmriat/Etha)）给了一个更彻底的答案：**不拼完整权重，让每个训练 rank 只把自己手里的分片，直接发给真正需要它的推理 rank——全程没有任何一张卡物化出完整张量。**

---

## 一、训推同步，卡在两座大山上

把训练集群的权重同步到推理集群，听起来只是"拷贝一下"，但在真实的大模型 RL 里有两个硬骨头。

**第一座山：显存。** 当前主流做法的同步粒度是"一个完整 weight"——要先用 all-gather 把被切碎的权重在某张卡上拼回完整张量，再拷进通信 buffer 发出去。对 MoE 的融合专家权重来说，这意味着每张卡额外占用 **2~3 倍最大权重** 的显存。模型越大、专家越多、越稀疏，这个"最大权重"只会越来越大，显存天花板水涨船高。

**第二座山：并行策略对不齐。** 训练侧可能是 TP×FSDP×EP 的复杂切分，推理侧（vLLM/SGLang）又是另一套 TP×EP。同一个张量，两边切法完全不同，怎么把训练的分片精确送到推理需要的位置，是个又繁琐又容易错的体力活。

## 二、Etha 的思路：只搬该搬的那一份

Etha 把这件事抽象成一句话：**`any (mesh, placement) → any (mesh, placement)`**——把一个用 PyTorch `DeviceMesh` + `Placement` 描述的张量，从一个独立启动的进程组，重分布到另一个独立进程组上完全不同的布局。这正是 `DTensor` 在单进程内做的事，Etha 把它推广到了两个互不相识的任务之间。

它有四个关键特性：

- **PyTorch 原生**：源和目标布局直接用 PyTorch 自己的 `DeviceMesh` + `Placement`，不引入任何新抽象、不需要学一套并行 DSL。
- **零拷贝**：Worker 到通信进程的交接走 CUDA IPC，直接对你注册的张量做 NCCL 收发，没有 host 中转、没有 staging buffer。
- **M-to-N 零冗余**：源 rank 把自己持有的分片直接发给需要它的目标 rank，**中间没有任何 rank 物化出完整张量**。
- **低侵入**：作为库接入现有训练/推理代码，实例化一个客户端、把张量交给它即可，不用改模型、不用重构分布式初始化。

其中最核心的，就是"M-to-N 零冗余"——它直接绕开了第一座山：既然从不拼完整权重，那个"最大权重"的显存天花板压根就不存在了。

---

## 三、零冗余是怎么做到的：get_m2m_map

要让"源分片直发目标分片"成立，关键是得先算清楚一张账：**同一个逻辑张量，源这边的哪一块、该发给目标那边的哪个 rank 的哪个位置。** 这张"搬运地图"由 Etha 的核心算法 `get_m2m_map` 计算。

![get_m2m_map 执行流程](etha_m2m_map.png)

它的思路很巧：

1. 源、目标的分片粒度往往对不齐，于是先取两者的**最细公共网格**（逐维 lcm），作为对账的统一单位；
2. 给这个网格的每个格子打上**全局唯一编号**；
3. 源和目标各自按自己的并行布局去切这张"编号表"，各自记下"我持有哪些编号、在我本地的哪个位置"；
4. 一次轻量的元信息交换后，**按编号对账**——同一个编号，源这边属于谁、目标那边属于谁，一目了然，搬运关系就此确定。

整张地图是**形状无关**的：同一对训练/推理布局只需算一次，之后每一轮权重同步都直接复用，不用重新规划。真正随张量形状变化的，只是把地图特化成具体分片、再打包成适合 NCCL 的传输单元这一层。**算一次，传 N 次。**

## 四、不只是省显存：zero-copy、低侵入、跨进程组

Etha 在工程上采用 Worker + Agent 的分离架构：你的训练/推理代码作为 **Worker**，只管把张量交出去；一个伴随的 **Agent 进程**独占 NCCL，负责实际收发；两者之间通过 CUDA IPC 零拷贝交接。

这个设计带来两个额外好处：

- **共卡也能跑。** 训练和推理共享同一张 GPU 时，同卡上只起一个 Agent，两个 Worker 都通过 CUDA IPC 把张量交给它——这张卡上只有一个 NCCL rank，天然避开了"同卡两进程跑 P2P 会死锁"的坑。
- **真正低侵入。** Etha 既能作为库直接嵌进你的进程，也能以这种 sidecar 方式运行，不强迫你改变现有的分布式初始化方式。

而且，源和目标本就是两个**独立启动**的任务（比如训练用 torchrun、推理是 vLLM 服务），Etha 通过一个轻量 KVStore 完成会合与布局元信息交换，把它们桥接成一次跨进程组的重分布。

## 五、和现有方案比，Etha 站在哪

业界的权重同步方案，大致分两条路线。

**一是"先拼完整权重再传"。** 先 all-gather 把每个 weight 在卡上恢复成完整张量，再发出去——传统的 gather-broadcast（verl 的 checkpoint engine 各后端 NCCL/NIXL/Mooncake，本质都属这一类）和 abcdabcd987 博客里的 gather-full + RDMA 方案都在此列。它们的共同代价是物化完整权重、受"最大权重"显存天花板限制。abcdabcd987 也坦言这么做"不是最快，但好写"，而且 gather 成完整张量后做投影融合、量化都更方便——本质是拿冗余换实现简单。

**二是"只搬该搬的分片"，也就是零冗余。** 不物化完整权重，源分片直发目标分片。蚂蚁开源的 AWEX 和 Etha 都走这条路——都靠预计算的 P2P 映射、分片直传、推理侧 in-place 更新。

| 方案 | 物化完整权重 | 显存 | 布局适配 |
|---|---|---|---|
| gather-broadcast（含 verl checkpoint engine） | 是，先 all-gather | 受最大权重限制 | 框架内适配 |
| abcdabcd987（gather-full + RDMA） | 是，`full_tensor` | 受最大权重限制 | PyTorch DTensor placement |
| AWEX（蚂蚁，零冗余） | 否，只传分片 | 无最大权重天花板 | 统一权重格式中间层 |
| **Etha（零冗余）** | **否，分片直传** | **无最大权重天花板** | **PyTorch (mesh, placement) 原生** |

Etha 和最接近的 AWEX 都做到了零冗余，关键区别在适配层：**AWEX 需要先把不同框架、不同并行策略的权重转成一层"统一格式"再传，而 Etha 直接复用 PyTorch 的 `DeviceMesh` / `Placement` 原语，不引入任何中间格式抽象**——接入更轻，也省掉一套格式转换的维护。

## 六、实战：给 vLLM 同步 Qwen3 MoE 权重

Etha 仓库里提供了一个完整可跑的例子：把一个训练端的 Qwen3-30B-A3B（MoE）权重，实时同步给一个在线的 vLLM 推理服务。这个例子一次性覆盖了真实场景的几个硬需求：

- **异构布局重分布**：训练端的 `(dp_replicate, dp_shard, ep)` 三维 MoE 切分，vLLM 端是 `(EP,)` 一维切分，Etha 一轮就完成跨边界的重新分片；
- **边界处 dtype 转换**：训练端 fp32 主权重，vLLM 端 bf16，Etha 在传输路上自动降精度，用户代码不用手动 cast；
- **零拷贝写进 kernel 槽位**：借助视图，NCCL 直接把数据写进推理 kernel 期望的内存位置，没有 staging buffer、没有收后再拷。
